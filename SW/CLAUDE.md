# Seedmate firmware - project rules

Offline cryptographic calculator (BIP39 seeds, Shamir, XOR, BIP85, BIP84) that is being extended to sign Bitcoin transactions (PSBT).
Hardware: PIC32MM0256GPM036 (256 KB flash, 32 KB RAM), XC32, MPLAB X project in `BIP39_MCC.X`, single configuration `v2`.
The old v1 hardware (PIC32MM0064GPL028) was removed from this branch; do not reintroduce `v1`/`v2` conditional compilation.

## Rule 1 - English only

All code written or modified for this project must be in English:
- identifiers (functions, variables, types, macros, files)
- comments (inline, block, Doxygen)
- log/debug strings, commit messages and documentation

Do not translate existing non-English code unless asked, but anything new must be English.

## Rule 2 - No git commits

Never run `git commit`, `git push`, or any other command that records or publishes changes. The user reviews the diff and makes all commits personally. Leave changes in the working tree and just summarize what changed; do not offer or ask to commit.

When the user asks for commit text, give it in this format, short:
- First line: a short summary, up to about 70 characters.
- A blank line.
- A body of a few lines, wrapped at about 72 characters (a sentence or two on what changes and why, and a short `-` list only if there are several separate changes). No file lists, no memory figures.
- English, as everything else (rule 1). List the new files that need `git add` (and any `-f` for ignored ones) outside the commit text, in the reply.

## Rule 3 - Memory is tight (RAM and flash)

Even on v2 the budget is limited. Every change must be justified against it.

v2 budget (last build of `Seedmate_v2`):
- Flash: 238 KB usable (0x9D004000, 0x3B800; the first 16 KB belong to the bootloader). Used about 206.1 KB (84.6% of the 238 KB left after the settings page); AES-GCM (about 7 KB) joins when the vault screens call it.
- RAM: 32 KB (0x80000000, 0x8000). Used about 22.3 KB (68.0%), and the reserved stack is about 12 KB.
- RAM address `0x80007F00` is the bootloader shared flag (`UPDATE_FLAG_ADDR`); never place data there.
- Biggest RAM users today: UR fountain decoder buffers `pure_parts` (8.7 KB) and `mixed_frames` (3.2 KB), `next_beams`/`current_beams` (1.5 KB each), `fast_bw_lookup` (1.3 KB), the loaded multisig wallet `ms_wallet` (0.6 KB).
- Biggest flash users: `.text` (about 78 KB) and the BIP39 word list string (about 13 KB).

RAM guidelines:
- Avoid large local arrays and big static buffers; reuse existing buffers (for example share scratch space between screens that are never active together).
- No dynamic allocation (`malloc`/`free`); the heap is only 512 bytes.
- No recursion; keep stack depth shallow, especially inside crypto code (secp256k1, bignum).
- Prefer the smallest integer type that fits; pack structs.
- Wipe secrets (seeds, keys, mnemonics, nonces) with `memzero` as soon as they are no longer needed.

Flash guidelines:
- Keep constant tables `const` so they stay in flash.
- Avoid `printf`-family and floating point; they pull in large library code.
- Do not add or enable crypto modules, curves, or wordlists that are not strictly needed.

After any change that adds code or data, rebuild `Seedmate_v2`, read the memory report (`dist/v2/production/*.map`, "Total ... used") and mention the flash and RAM delta in the summary.

## Rule 4 - Transparency and user control come first

The user must always see what the device is doing and stay in control. This is a priority in both the interface and the flow logic, on the same level as security:
- Never sign, write to the SD card, export or change anything without an explicit confirmation step that shows what will happen (amounts, destinations, which keys/inputs).
- Long operations (key derivation, checks, signing, file I/O) show a progress bar plus the step currently running (for example "INPUT 2 OF 3", the derivation path, "SIGNING", "VERIFYING SIGNATURE").
- When something is refused or fails, say why on screen in plain words ("PREV TX MISMATCH", "SWITCH TO MULTI SIG"); never fail silently or fall back to a different action.
- Show verified facts and unverified claims differently (colors, "VERIFIED" / "NOT VERIFIED" labels); do not present data from the PSBT as checked when it was not.
- Every flow can be cancelled with BACK before any irreversible step.

## Rule 5 - No real wallet data in the repo

Never put data from the user's real wallets (xpubs, descriptors, fingerprints, addresses, QR captures or exports) in source, test or documentation files, not even temporarily: it reveals the wallet's addresses and balances. Test data comes from generated test seeds ("abandon x11 about" and seeds derived in the Python generators). If the user shares a real export to show a format, use it only to learn the format and rebuild an equivalent from test keys.

## Rule 6 - Button grid on every screen that waits for a key

Whenever a screen waits for a key, show the button grid (bottom right, x 63-153 from `GRID_X` in `screens.h`, y 105-125: BACK, UP, OK on the top row, LEFT, DOWN, RIGHT on the bottom row) with what each button does on that screen, and only the buttons that do something. Do not describe keys in text footers ("OK=SIGN BACK=CANCEL", "PRESS ANY KEY"). Use the helpers in `screens.c` (`grid_menu2()`, `grid_OK_back()`, `grid_confirm()`, `grid_labels()`...) and add a new `grid_*()` there when no existing one fits. Lay out the screen so nothing is drawn inside the grid area (progress bars go above it, at y 92-97); only full-screen QR codes may leave it out, and the start screen, which keeps "PRESS ANY BUTTON" under the logo on purpose. Label OK (and BACK) with the action when it is specific ("QR", "SAVE", "STOP", "UPDT"), not a generic "OK".

## Rule 7 - Consistent colors

Every color has one meaning on every screen; reuse it, never pick a color for looks:
- WHITE: normal text: menu options, values and data (words, addresses, xpubs, amounts), labels of keys and the explanations in the body of a screen. Light gray `ST7735_LIGHTGREY` (0xC618, `screens.h`): only the screen title, the top line, always drawn centered with `draw_title()` (`draw_title_pair()` when a second part shares the line, e.g. "INPUT 1/3" and the script type); error and success screens keep a red or green title, also centered. The main menu has the title "SEEDMATE". Dark gray `0x8410`: disabled items and decoration (key outlines).
- YELLOW: warnings and unverified data ("NOT VERIFIED", "AMOUNTS NOT VERIFIED", warnings that do not stop the flow), and the fee.
- ORANGE: only the selected item or cursor (menus, keys, editable fields). Not for titles, hints or amounts.
- GREEN: success and verified facts ("VERIFIED", "OK", "LOADED", our own key or fingerprint), also as the title of a success screen.
- RED: errors, refusals and dangerous actions ("PSBT PARSE ERROR", "KEY MISMATCH", wipe), also as the title of an error screen.
- CYAN: secondary information and progress (derivation paths, counters, active layer), and what the device is doing right now ("DERIVING THE KEYS", "READING SD CARD...", "SCANNING...", the running step above a progress bar).
- Progress bar: white outline, green fill.
Texts are upper case. Before adding a screen, look at a similar existing one and copy its colors.

## Building and checking (no IDE needed)

The project builds from the command line with MPLAB X's `make` and XC32 v5.10 (`-O1 -ffunction-sections -fdata-sections`, linked with `--gc-sections`, no LTO, and `-Werror -Wall`, so any new warning breaks the build). From `BIP39_MCC.X`:

```bash
export PATH="/c/Program Files/Microchip/MPLABX/v6.35/gnuBins/GnuWin32/bin:/c/Program Files/Microchip/xc32/v5.10/bin:$PATH"
make -f nbproject/Makefile-v2.mk SUBPROJECTS= .build-conf
```

Add `-B` to force a full rebuild. The memory totals are in `dist/v2/production/BIP39_MCC.X.production.map` ("Total kseg0_program_mem used" and "Total Data Memory used"). `nbproject/Makefile-*.mk` are generated by MPLAB X from its in-memory project model. If the IDE has the project open, editing `configurations.xml` by hand is NOT picked up: MPLAB regenerates the makefile without the new file and may overwrite the XML on save. When a source file is added or removed, tell the user to add it in the IDE (Source Files > Add Existing Item) or to close and reopen the project before building.

With the project closed in the IDE, edit `configurations.xml` and regenerate the makefiles exactly as MPLAB would (no hand patching), from `SW`:

```bash
"/c/Program Files/Microchip/MPLABX/v6.35/mplab_platform/bin/prjMakefilesGenerator.bat" "BIP39_MCC.X@v2"
```

## Source layout (`src/`)

- `main.c` - application core: a `state_t` state machine in `main()`, entropy sources (coins, dice, words, cards, timer), SD card driver over SPI3, BIP39 helpers, BIP85, BIP84 (xpub/addresses), Shamir/XOR/obfuscation, text editor, and `scan_ur_message()` which rebuilds a UR message (`ur:crypto-psbt` for SIGN, `ur:crypto-output` for IMPORT DESCRIPTOR) from animated QR frames received on UART2 from a GM861 scanner.
  Menus: the main menu has 8 entries (CREATE, LOAD, BIP85, OPSEC, TOOLS, SD CARD, RESOURCES, SETTINGS); OPSEC holds Shamir, XOR, obfuscation and cards, TOOLS the QR reader, QR from text, EFF password and REVIEW PSBT. `cMAIN_*` are function ids kept in `main_pointer` while a flow runs (the flows test it), the menus map their positions to them (`main_menu_ids[]`, `opsec_menu_ids[]`, selection in `main_sel`, `opsec_pointer`, `tools_pointer`); `MAIN_RUN` runs the chosen function and `transition_to_main()` returns to OPSEC after an OPSEC flow.
  SEED BACKUP: the LEFT arrow of the words screen (label "SEED BACKUP") opens `BACKUP_MENU` (SD, SEEDQR, COMPACT SEEDQR, VERIFY TRANSCRIPT; `menu_backup[]`, `draw_backup_menu()`: its BACK key is labelled LIST since it returns to the words). VERIFY TRANSCRIPT (`transcript_verify()`) checks the paper copy: every word in order, four choices each (the right one and three of the 12 words around it in the alphabetical list, so a word copied wrongly is the one picked; random order), the cursor in orange; BACK returns to the list, a wrong word says which one in red and returns to the whole list, all right gives "TRANSCRIPT VERIFIED" in green. LOAD (OK or RIGHT) on the words of a seed just made with CREATE asks for it first (`show_seed_load()`, `transcript_pending()`), with a red "SKIP AND LOAD" row below the words, reached only going down; once verified or skipped the seed is remembered (`transcript_tag`, a short hash of the entropy, wiped in `transition_to_main()`) and LOAD does not ask again; loaded seeds are never asked. SEEDQR and COMPACT SEEDQR are blocked with the reason on screen (`print_blocked()`) when the SEEDQR setting is off, otherwise the red warning comes first, every time; the viewer (`VIEW_QR`, `draw_seed_qr_view()`) shows the code full screen, OK zooms into one tile (`draw_qr_view()` in `screens.c`: at most 15 modules per tile side, neighbouring tiles share one module, grid lines, row/column numbers every 5 modules; 2x2 tiles for a seed QR) and the arrows move between tiles. SD is blocked when SD WRITE is off, otherwise a yellow warning (`print_sd_warning()`: not encrypted, erase after use or keep the card apart from this device) precedes the slot list. Seeds are written only to slots 2..200 (sectors 1..199, `cSD_WRITE_LAST_SLOT`): slot 1 (sector 0) belongs to older firmware and is read only, and nothing else on the card is touched. A slot that already holds a valid seed (checksum as `sd_write_seed()` writes it) asks for confirmation first ("SLOT n IS IN USE", BACK / OVER); `sd_write_seed()` wipes the sector buffer afterwards. The SD slot format is XOR with one byte plus a checksum: obfuscation, not encryption.
  SD card layout (`app_defs.h`): sector 0 is the legacy slot 1 (read only), sectors 1..199 are seed slots 2..200 (ERASE SECTOR only accepts these: "NOT A SEED"), the vault header is sector 501 and its records 502..2046 (`vault.h`, `docs/vault.md`), and sector 2047 (`cSD_MARKER_SECTOR`, last of the first 1 MB, never used by older firmware) holds the marker "SEEDMATE" + format version + complement of the sum of those 9 bytes (`sd_marker_build()`, `sd_marker_valid()`). The SD CARD menu (`menu_erase[]`) has ERASE SECTOR, INITIALIZE CARD and WIPE ALL CARD. INITIALIZE CARD (`sd_initialize_card()`, red warning first, progress bar with the step: erasing the first 1 MB, writing the vault header, writing and verifying the marker) zeroes sectors 0..2046, so it destroys the seeds, the vault and any file system, writes an empty vault header with a new `vault_id` and a random first counter (`vault_new_id()`: SHA256 of the Shamir key press pool `sss_entropy_pool`, TMR1, the core timer and "VAULT"; the pool is cleared afterwards since both are public) and reads it back, and writes the marker last; WIPE ALL CARD (red warning with the card size) overwrites every sector, marker included, so the card becomes uninitialized. Seed writes require a valid marker (`sd_marker_state()`, checked when SD is chosen in SEED BACKUP and again before each write, "CARD NOT INITIALIZED" / "USE SD CARD > INITIALIZE CARD"); reads of slots never depend on the marker, so cards from older hardware still load. Keep one card only for seeds and never put it in a PC (a PC would offer to format it); use another FAT16 card to move PSBTs, descriptors and firmware.
  TOOLS: QR READER (`reader_open()`, `QR_READER`) reads one code with `qr_read_raw()` (stored scanner setup, UART2 interrupt ring, spaces and binary kept, into the fountain buffer, wiped on exit) and only shows it: a type label for information (text or binary size, bitcoin address, payment URI, one UR part, yellow "LOOKS LIKE A SEED" / "COMPACT SEEDQR"), the content wrapped in pages (UP/DOWN), binary in hexadecimal; nothing is loaded or saved. QR FROM TEXT (`text_qr_edit()`) edits up to `cTEXTQR_MAX` (320) characters in the note editor, kept in `buffer` while shown, then shows the QR in the same viewer as the SeedQR (zoom by tiles, so a passphrase QR can be copied by hand), the smallest version up to 11 with error correction M, or L if M does not fit (`draw_text_qr_view()`; the QR library does not check capacity, `text_qr_bits()` does); a text that is a seed (`text_looks_like_seed()`: 12-24 BIP39 words or 48/96 SeedQR digits) gets a red warning first, whatever the SEEDQR setting; BACK from the QR returns to the text, CANCEL in the editor wipes it.
  REVIEW PSBT (TOOLS, `psbt_inspect_only`): the same FROM QR / FROM SD menu and PSBT viewer as SIGN, without a seed and without signing: no SIGN in the grid (OK does nothing), the summary says "NO SEED: KEYS NOT CHECKED" and key lines show "FP xxxxxxxx NOT CHECKED" in yellow; BACK from the menu returns to TOOLS. SIGN and IMPORT DESCRIPTOR in the wallet menu clear the flag.
  EFF PASSWORD (TOOLS, `eff_open()`, `EFF_CONFIG` / `EFF_ROLL` / `EFF_RESULT`): 1..12 words (`cEFF_MAX_WORDS`) of the EFF Short Wordlist 1, each from 4 dice entered on the 1-6 keys (LEFT/RIGHT, OK, DEL removes the last die or the last word); the index is the dice number, as in the printed list, so it can be checked by hand; the dice are the only source of the words. Optional NUMBERS: one digit after each word from the timer when the word is completed (`timer_digit()`), said on screen. The words are shown in lower case on the dice screen and in the result (exactly as typed, unlike the other upper case texts), one space between words; the configuration screen shows the entropy of the result as one total ("ENTROPY: n BITS", rounded down: 10.34 bits per word, 13.66 with the digit), updated with each change; OK shows its QR in the zoomable viewer (`qr_from_eff`: BACK returns to the result). The EFF code no longer uses `buffer` for itself (TOOLS keeps the result text there while it is shown). Everything is wiped on exit. The list (`EFF_short.c`) is generated by `../test/eff/gen_eff_short.py` from the official file (SHA-256 8f5ca830...ae69) and `../test/eff/test_eff.c` rebuilds that file from the firmware list and checks the hash; do not edit the list by hand.
  Text editor (`full_text_editor()`, BIP39 passphrase and notes): 3 alphabetical rows of 9 outlined keys plus CANCEL/SAVE and a last row split in RETURN / QR / die (`KBD_QR`, `KBD_DIE`), the 2x3 control keys (aA, #@, cursor arrows) next to the untouched `grid_keyboard()`; NUM and SYM layers hold each printable ASCII symbol once. QR (`editor_qr_read()`) opens the QR READER screens in insert mode ("INSERT FROM QR", `reader_insert`): the text is shown in full with its length and ADD inserts it at the cursor (title or text) only if it is printable ASCII (line breaks only in the note text, CR dropped) and fits what is left, otherwise the reason in red; it reads into the last 512 B of the fountain buffer (the editor text is in `buffer`, a vault list at the start of the fountain buffer). The die runs the EFF PASSWORD screens as a blocking call (`eff_generate()`, same `eff_key_press()` handler as TOOLS, `wait_any_key()`) and inserts the password at the cursor, or says it does not fit ("NOT INSERTED"). Passphrase mode adds a character counter and a review screen after SAVE (BACK edits again); `edit_bip39_passphrase()` edits a copy, so CANCEL keeps the old one, and `transition_to_main()` wipes it.
  XOR and Shamir merge ask the source (keyboard, SD, QR) before each input: `print_input_menu()` shows "SEED n OF m FROM" / "SHARE n OF k FROM" and the inputs already loaded, and every source ends in `multi_input_store()` (size check against the first input, XOR or interpolation after the last one); `multi_input_wipe()` clears the inputs at the start, on cancel and after the result.
  BIP84/BIP48 keys are derived only when the user opens the wallet menu from the words screen (`load_wallet_keys()`: loading screen with progress phases, BACK cancels the PBKDF2). The key cache is bound to the seed on screen by `bip84_seed_tag` (truncated SHA256 of entropy, size and passphrase), so another Shamir share or a BIP85 child is never shown with stale keys.
  Wallet menu (`menu_bip84[]`, `menu_bip84_multi[]`, option ids `cBIP84_*` mapped by `bip84_single_options[]` / `bip84_multi_options[]`): SIGN, DERIVE, VAULT, XPUB/ZPUB, ADDRESSES (IMPORT DESCRIPTOR in multisig), PASSPHRASE, ACCOUNT, MODE, UNLOAD SEED; no title (the MODE entry says single or multisig, and 9 entries fit from y=10), circular (UP on the first goes to the last and back). UNLOAD SEED and BACK on the words screen both go through the same red confirmation (`print_unload_confirm()`, `CONFIRM_UNLOAD`, BACK returns where it came from); WIPE clears every copy of the seed and of what derives from it (entropy, triple backup, XOR inputs, Shamir coefficients and shares, BIP85 child, card sequence, dice string, the static copy in `append_checksum()`, the SD sector buffer and the fountain buffer), then `transition_to_main()` wipes the passphrase, keys and multisig wallet and shows the main menu. XPUB/ZPUB shows the key with its origin, LEFT / RIGHT switch xpub and zpub (the grid names the other one), OK shows its QR: by default the same text "[fingerprint/84h/0h/nh]xpub" (or zpub, or the 48h/0h/nh/2h multisig key), which Sparrow and Nunchuk read (Nunchuk does not read UR crypto-account: libnunchuk takes that text or UR:BYTES with a Coldcard/Passport JSON); LEFT / RIGHT on the QR switch to UR crypto-account and back (`xpub_qr_ur`, format named in the right margin). The master fingerprint and the account are always shown at its bottom left, so there is no FINGERPRINT entry. VAULT (`vault_run()`, a modal flow like the editor, back to the wallet menu) opens the vault of the card with the cached `vault_key` ("VAULT xxxxxxxx" with the master fingerprint, "READING THE ENTRIES", "ENTRY n OF m" and bar); a card initialized before the vault (blank sector 501) is offered "CREATE AN EMPTY VAULT" (`vault_create()`). List (`vault_draw_list()`): titles sorted, NEW ENTRY last, counts at the bottom left (other keys' records as "+n OTHERS"), grid LOAD / DEL / EDIT, or NEW on NEW ENTRY. NEW ENTRY offers NOTE, LOGIN, PASSPHRASE, CREDIT CARD (templates, cursor on the title, `editor_title_first`), EFF PASSWORD (`eff_generate()`, then "PASSWORD: ..." as a LOGIN) and MULTISIG DESCRIPTOR (`vault_new_descriptor()`: FROM QR, the IMPORT DESCRIPTOR scan checked with `descriptor_check()` and saved without changing the active wallet, or CURRENT MS DESCRIPTOR, the active `ms_wallet`, dark gray when there is none; `vault_save_descriptor()` packs it with `desc_pack()` into one record, or two for 6-7 cosigners, no editor: title "MULTISIG m OF n XXXX", one confirmation with the fingerprints); LOAD of such an entry (`vault_load_descriptor()`) unpacks it and goes through `descriptor_check_and_load()` like IMPORT DESCRIPTOR (multisig mode only, "SWITCH TO MULTI SIG"), DEL frees both records; SAVE asks "SAVE TO VAULT" (BACK edits again, "TITLE NEEDED" without a title) and writes through `vault_reserve()` / `vault_write_record()` / `vault_commit()`; EDIT saves a new version and frees the old one; LOAD (`vault_view()`) shows the text in pages (QR READER page code), OK its QR (title and text, text only for PASSPHRASE, red seed warning if it is a seed; `vault_qr_view()`); DEL has a red confirmation. Errors as `vault_error()`; a changed or unreadable card leaves the vault. RAM: the list, the bitmap copy and the parked text of a write live at the start of the fountain buffer (word aligned), `buffer` does the SD I/O and holds the text while editing or viewing; all wiped on exit. PASSPHRASE opens PASSPHRASE FROM (`menu_passphrase[]`, `PASSPHRASE_MENU`): FROM KEYBOARD is the text editor on a copy (CANCEL keeps the old passphrase), FROM QR reuses the QR READER screens (`reader_open(true)`, `reader_passphrase`): the text read is shown in full with its length and OK ("USE") makes it the passphrase only if it is printable ASCII on one line and fits `bip84_passphrase` (otherwise the reason in red), FROM VAULT (`vault_pick_passphrase()`) opens the vault of the seed and passphrase on screen and lists only its PASSPHRASE entries; the chosen one is shown in full and USE takes it under the same rules as FROM QR (`vault_use_passphrase()`); a new passphrase derives the keys again (`PRECOMPUTE_BIP84`). DERIVE opens a submenu (`derive_menu_run()`, `menu_derive[]`): BIP85 CHILD SEED, BIP85 PASSWORD and NOSTR KEYS, each deriving the BIP32 root of the seed and passphrase on screen again (`derive_root_screen()`, BACK cancels the PBKDF2) and showing "FROM FINGERPRINT xxxxxxxx" (green when it is the wallet loaded). BIP85 PASSWORD (`bip85_password_run()`): format BASE64 (707'764, 20-86 characters) or BASE85 (707'785, 10-80), length (21 by default, as Coldcard and Krux) and index, kept for the session; the account does not change it, the passphrase does; the password is shown in groups of 4 (`draw_grouped()`), OK its QR, a yellow note that it is a secret. NOSTR KEYS (`nostr_keys_run()`): NIP-06 m/44'/1237'/account'/0/0 with the account of the wallet menu; the npub first (public, cyan "SAFE TO SHARE"), RIGHT shows the nsec after a red warning every time, LEFT back to the npub, OK the QR of the one on screen; everything wiped on exit. BIP85 CHILD SEED (`derive_child_seed()`) asks size and index (the same `CHILD_CONFIG` screen as BIP85 in the main menu, `derive_from_wallet`), derives the BIP85 child from the BIP32 root of the seed on screen WITH its passphrase (as Krux does: the child changes with the passphrase; the BIP85 spec derives from the root key, so this is the same thing), shows "DERIVED FROM FINGERPRINT xxxxxxxx" (taken from the root actually used), then the child's words; BACK returns to the wallet menu with the parent untouched, LOAD makes the child the seed on screen (the passphrase is dropped, `main_pointer` becomes BIP85). BIP85 CHILD SEED in the main menu is unchanged (mnemonic typed or loaded, no passphrase, no extra text); both use `bip85_derive_entropy()`. Never show "PASSPHRASE: YES/NO" texts: the user knows whether there is one.
  GM861 scanner (UART2, 115200, manual "GM861S User Manual V1.2.4", zone bits in chapter 10): its stored setup is command triggered mode with a 500 ms break between reads. For the UR animated scan only, `scan_ur_message()` writes to the scanner RAM (never its flash, `gm861_override()`): 0x0000 continuous mode, 0x0005 break 0, 0x0013 same-code delay 500 ms, 0x0060 CR tail; it receives through the UART2 interrupt into a 512 B ring buffer (`scan_rx_*`, the 4-byte hardware FIFO would overflow while a frame is processed) and restores every register on exit, mode first (`gm861_restore()`, error shown if it fails). If the setup fails it falls back to command trigger mode (trigger after each processed code, wait for the 7-byte ACK, resend after 50 ms). Frame end = CR or 15 ms of silence, timed with the core timer (`_CP0_GET_COUNT()`, 12 MHz). Other QR functions keep polled UART and the stored scanner setup.
- `settings.c/h` - permanent settings (decoy game on/off, SeedQR on/off, SD WRITE on/off; SeedQR and SD WRITE default to off, each needs the red or yellow warning before it is turned on): records of 8 bytes in a log in the last 2 KB page of the program flash (0x1D03F800), reserved in the app linker script (`LENGTH 0x3B800`) and excluded from what the bootloader erases and writes (`HEXFLASH_APP_PHYS_END`), so they survive power off and firmware updates. Flags are stored as 1 = factory default (a blank page is the defaults), the newest valid record wins, the page is erased only when its 256 slots are full, and the only function that writes flash takes a slot number. Never store seeds, keys, passphrases or anything secret there: the claim is that the device keeps no secrets, only these preferences. Every change is confirmed on screen as permanent (`print_setting_confirm()`, `CONFIRM_SETTING`), a failed write is reported (`SETTING_FAILED`). Host test `../test/settings/test_settings.c` (mock flash: no double write of a slot, rotation, half written records).
- `snake.c/h` - decoy: at power-on `main()` runs a snake game (`snake_run()`, never returns) unless OK + RIGHT are held while the device starts or the user turned it off in SETTINGS (`decoy_enabled`, permanent; `DECOY_SNAKE` in `snake.h`, 0 removes it at build time). Checked after the LCD init and before the splash screen, so nothing Seedmate-like is shown; no SD, scanner or secrets touched; the board lives in the fountain part buffer. Fullscreen game, exempt from rules 6 and 7 on purpose. Do not confuse with the bootloader combination (OK + BACK at power-on = forced update).
- `screens.c/h` - TFT drawing only: bitmaps, menu text tables, grids/arrows, menus, QR views and input screens. The start screen (`print_logo()`) draws the logo of `web/img/logo.png` from its 6 rectangles (two interlocking S halves, scaled to 64 px, its own orange `LOGO_ORANGE`, a brand color allowed on this screen only): black screen, the halves slide in from the sides and lock in the middle (ease out, only the strip each piece leaves is cleared), then "S E E D M A T E", "PRESS ANY BUTTON" and the version at the bottom right. The old warnings there are given where they apply (SeedQR and seed text warnings, the SD warning); the green/red camera icons keep their colors as the explanation. Menus have a title on the top line: `print_generic_menu()` takes it from `menu_title()` (reusing the strings of other menus, e.g. `menu_main[]`), `print_titled_menu()` when it depends on the context; options start at y=13. Screens that still mix drawing with mnemonic/SD/BIP84 logic remain in `main.c` until `mnemonic.c`, `sd_card.c` and `bip84.c` exist.
- `app_defs.h` - application constants (menu sizes/indices, option values, messages, `cVersion`). `app_state.h` - `extern` declarations of the state variables that `main.c` owns and `screens.c` reads. Keep it small; prefer passing parameters in new code.
- `psbt.c/h` - zero-copy PSBT (BIP174 v0) parser: inputs/outputs, amounts, fee, BIP32 derivations, sighash, partial signatures, multisig scripts. No crypto inside; key verification against the seed lives in `main.c` (`psbt_check_owner`). Host tests in `../test/psbt/`.
- `psbt_sign.c/h` - signing crypto: BIP143 sighash (P2WPKH and P2WSH), NON_WITNESS_UTXO txid check, ECDSA with RFC6979 nonces, low S and low R grinding, verified after signing, built on the vendored bignum/ecdsa (the trimmed `crypto/ecdsa.c` has no signing), and BIP32 public child derivation (`psbt_public_ckd()`, for cosigner xpubs). Host tests (`../test/psbt/test_sign.c`) check the BIP143 vector and that the firmware signs the abandon PSBT byte-identically to the Python signer. The decision of what to sign (`psbt_plan_signing`: mainnet only, SIGHASH_ALL only, txid check, key/change verification, confirmation screen) and key derivation live in `main.c` (`psbt_review_and_sign`).
- `descriptor.c/h` - multisig wallet descriptor parser, no crypto: output descriptor `wsh(sortedmulti|multi(...))` (BIP380 checksum verified when present, keys ending in /<0;1>/*, /0/* or /1/*) and the Coldcard multisig setup file (Policy/Format/Derivation, xpub or Zpub), and the CBOR of a UR crypto-output (BCR-2020-010, Sparrow's animated "Output Descriptor" QR, also read by Krux/SeedSigner/Jade; `desc_parse_cbor()`, iterative CBOR skip, v1 and v2 tags). Mainnet P2WSH only, up to `DESC_MAX_KEYS` (7) cosigners. `desc_pack()` / `desc_unpack()` give the compact binary copy the vault stores (86 bytes per key, strict unpack). IMPORT DESCRIPTOR in the multisig menu opens the SIGN submenu with a third source (FROM QR / FROM SD / FROM VAULT, `menu_import[]`, `sign_menu_descriptor`; FROM VAULT is `vault_pick_descriptor()`, the vault list of DESCRIPTOR entries, the same pick list as PASSPHRASE > FROM VAULT, `vault_pick_type()`): FROM QR scans the animated `UR:CRYPTO-OUTPUT/` with the same scanner as PSBTs (`scan_ur_message()` takes the UR type), or a static QR: `scan_descriptor_qr()` reads the first code like QR READER (`qr_read_raw()`, stored scanner setup, 50 ms end of code, into the fountain buffer: a long dense code arrives whole, which the continuous UR scan does not manage) and takes a single part `UR:CRYPTO-OUTPUT/` (the QR of the PDF Sparrow prints is one, about 1,300 characters; `ur_decode_single()` in `ur_encode.c`, in place, CRC checked) or the descriptor text (`desc_parse()`), and hands a frame of the animated one over to the UR scan; "CHECKING THE DESCRIPTOR" stays on screen until the review; the UR scan also takes single part codes (small PSBTs); BACK stops `qr_read_raw()` while it waits for a code; any other code read during a UR scan is named on screen (`scan_notice()`: "NOT A UR:CRYPTO-PSBT QR", "BBQR NOT SUPPORTED YET", "QR TEXT TOO LONG") instead of being ignored, FROM SD reads a .TXT (`import_descriptor_from_sd()`); both go through `descriptor_check_and_load()`, which refuses the wallet unless this seed's m/48'/0'/n'/2' xpub is one of the keys ("SWITCH TO ACCOUNT n", "MY KEY DOES NOT MATCH"), shows policy, checksum, fingerprints and receive address 0 to compare, and on OK keeps it in RAM (`ms_wallet`, bound to the seed tag and account, wiped in `transition_to_main()`). While it is active, multisig inputs and change are checked against the script built from every cosigner xpub (`psbt_public_ckd()` in `psbt_sign.c`, `desc_witness_script()`): matching change counts as change, other outputs as sent, inputs of another wallet are refused ("INPUT NOT IN WALLET"). Host tests `../test/psbt/test_descriptor.c` with data from `gen_descriptor.py` (also the wallet as crypto-output CBOR with v1 and v2 tags), which also writes SD test files (MSDESC.TXT, MSCOLD.TXT, MSWALLET.PSB, MSATTACK.PSB) for the "abandon x11 about" seed.
- `sd_files.c/h` - read-only FAT16 file access (root directory, 8.3 names) over Petit FatFs, plus the pff disk interface on top of `sd_read_partial()` in `main.c`. Used to load PSBTs (`.PSB` binary or `.TXT` base64) and multisig descriptors (`.TXT`) into the fountain buffer (`fountain_scratch_buffer()`); `sd_pick_file()` in `main.c` is the shared file list.
- Bootloader (`../../bootloader`, first 8 KB of flash, built with `make -f nbproject/Makefile-default.mk BUILD_SUBPROJECTS= .build-conf`, which also writes `bootloader.production.unified.hex` with the current app for the PICkit): version `BOOT_VERSION` in `boot_ui.h` (top right of every bootloader screen, and as the 16 byte tag "BOOT 1.0" in the last 16 bytes of the 8 KB main flash, 0x9D001FF0, that the app reads in SETTINGS (it is NOT in the boot flash: an app read of it there hung the device), `BOOT_TAG_ADDRESS` in `app_defs.h`; "BOOTLOADER ?" when an older bootloader has none; MAJOR changes with the flash layout, MINOR with behavior; bump it with any bootloader change), shows each step on the LCD (the last flash page, 0x1D03F800, is never touched: it holds the app settings) (`boot_ui.c` compiles the app's `TFT.c`, `spi_boot.c` its `SPI.c`; both are placed in free boot flash through its cached alias 0x9FC004B0/0x9FC01190 by the bootloader linker script, with the update flow helpers; the 8 KB main area (usable 0x1FF0) is full to 4 B (: the next bootloader feature needs the 16 KB layout), the boot flash code area at ~92% and its data area full; `SPI()` is declared noinline in `spi_boot.c`: inlined into `command()`/`send_data()` the LCD ignores the commands and stays black), shows the SHA-256 of the whole `UPDATE.HEX` (`boot_sha.c`: compact own implementation, tested against hashlib in `../../bootloader/test/test_boot_sha.c`; code in two gaps of the boot flash between the vectors, 0x9FC00140 and 0x9FC0038C, `K` table in main flash; the hash is of the file bytes, so `certutil -hashfile UPDATE.HEX SHA256` gives the same) before asking OK/BACK to erase, hashes the file again while writing and erases the app again if it differs from what was shown, and flashes `UPDATE.HEX` from the SD when the app sets the flag at `0x80007F00`, when there is no app (blank reset vector: factory state with only the bootloader, or an update that failed after erasing; then OK after any result restarts and retries), or when OK + BACK are held at power-on (forced update, 10 fast LED flickers; recovers a broken app without a programmer). LED blink codes at the end: 7 success, 4 SD read error, 5 bad record or missing end, 6 flash error, 8 empty flash, 9 "HEX NOT FOR THIS DEVICE" (`hexflash_check_record()`: any data outside the app area 0x1D002000-0x1D03FFFF, which covers the bootloader, the config words and the hex of another hardware, or no program at the reset vector); the whole file is read and checked first (record checksums, end record, SD reads) without touching the flash, so a damaged card or file leaves the current app working; only then is the app area erased and programmed, and an error during that second pass leaves no app (use the forced update). Host test `../../bootloader/test/test_hex_flash.c` (feed it the app hex).
- `pff_app.c` - compiles `../../bootloader/src/pff.c` for the app (Petit FatFs is shared with the bootloader, not copied). `pffconf.h` is shared too: a change there also changes the bootloader, so rebuild both and check the bootloader still fits its 8 KB.
- `ur_encode.c/h` - UR encoder: `crypto-psbt` for exporting PSBTs as animated QR (pure parts only, uppercase minimal Bytewords for QR alphanumeric mode, no buffers) and `crypto-account` (BCR-2020-015, `ur_account_cbor()`) for the UR option of the XPUB QR: master fingerprint, origin path, chain code and parent fingerprint as `wpkh(hdkey)` or `wsh(cosigner(hdkey))`. The BIP84 menu account index (`bip84_account_index`, 0..255 so the QR stays one version 8 code) applies to `m/84'/0'/n'` and `m/48'/0'/n'/2'`; the coin-level nodes are cached so changing it skips the PBKDF2. Also owns the shared CRC32 (`ur_crc32_update`) and the single part UR decoder (`ur_decode_single()`). Host tests in `../test/psbt/test_ur.c`, including a byte-exact match against frames captured from Sparrow. Test data (`ur_test_psbt.h`: PSBT signed by the independent Python signer `sign_abandon.py`, plus its public test key) lives in `../test/psbt/`, not in the firmware.
- `fountain.c`, `sampler.c`, `prng.c`, `bytewords.c` - UR fountain-code decoder (Xoshiro256 PRNG and alias sampler). They are only for decoding UR frames and must never be used for entropy.
- `TFT.c`, `SPI.c` - ST7735 160x128 display driver.
- `sha256.c`, `sha512.c`, `SSS/` (Shamir, `memzero`), `QRCode-master/` (QR encoder), `words_opt.h` (BIP39 word list as one continuous string).
- `bip85.c/h` - BIP85 entropy of a hardened path from the BIP32 master key (`bip85_entropy()`, optional progress callback): the child seeds (`bip85_derive_entropy()` in `main.c`), the vault key and the passwords (`bip85_password()`: PWD BASE64 and PWD BASE85, the RFC 1924 alphabet of Python's b85encode). Tested against the BIP85 spec vectors in `../test/vault/` and `../test/derive/`.
- `nostr.c/h` - NIP-19 npub / nsec strings of a 32 byte key (`nostr_bech32()`, bech32 of `crypto/segwit_addr.c`); the NIP-06 derivation is BIP32 in `main.c`. Host test `../test/derive/test_derive.c` with `gen_derive.py` (independent Python secp256k1 and bech32, checked against the BIP85 and NIP-06 vectors), also for the passwords.
- `vault.c/h` - vault crypto and format, no SD access and no UI (spec in `../docs/vault.md`): key = BIP85 HEX 32 bytes index 8377 (`vault_derive_key()`, computed in `bip84_derive_keys()` with the wallet keys into `vault_key`, wiped in `transition_to_main()`), header sector (`vault_header_init()` / `vault_header_valid()`: "SMVAULT", version, counter, `vault_id`, bitmap, CRC32), records sealed / opened in place in a 512 B sector with AES-256-GCM (`vault_record_seal()` / `vault_record_open()`: nonce = counter + sector, AAD = the 8 plain header bytes, so a record moved to another sector is refused). The first `write_counter` is random (from `vault_new_id()`), so two cards with a vault of the same seed never share nonces. Format layer on top (`vault_open()`, `vault_scan()`: list of our entries sorted by title, others counted; `vault_reserve()` → `vault_write_record()` → `vault_commit()`, `vault_delete()`): the header records the nonces as used before any record is written, every record is read back and decrypted, and every write first checks marker, `vault_id` and counter ("CARD CHANGED"); a header with a bad CRC is never written. It keeps only `vault_id` and the counter in RAM, works in the caller's 512 B buffer, and reaches the card through `vault_io_read()` / `vault_io_write()` / `vault_io_marker_valid()` in `main.c`. AES/GCM are the vendored Gladman files in `crypto/aes/` (256 bit key schedule only, no tables, GHASH without tables) plus `crypto/consteq.c`; two local edits there are marked "Seedmate" (`#undef v2` in `aestab.c`, `aes_encrypt_key256()` in `gcm_init_and_key()`). `tc_fault_handler()` in `main.c` stops the device with "FAULT DETECTED" (the trezor no-op handler is not linked). Host test `../test/vault/test_vault.c`, byte-exact against the Python reference `gen_vault.py` (cryptography's AESGCM), which writes `vault_vectors.h`, plus the format on a mock card (edit, delete, failed and corrupt writes, swapped card, damaged header, full vault, two-part entries, no nonce ever reused).
- `crypto/` - third-party trezor-crypto (bip32, secp256k1, ecdsa, base58, segwit_addr, ...). Treat as vendored: avoid editing it, and only link what is needed.
- `config/v2/` - MCC/Harmony generated code and the linker script `p32MM0256GPM036.ld`. Do not hand-edit generated files unless necessary.
- `main _derive.c`, `main_intento e ir a crypto.c`, `main_wipe_v1.c`, `main.c.bak` - old snapshots, not part of the build; do not edit them.
- `../test/` - host-side test benches.
