# Seedmate firmware - project rules

Offline cryptographic calculator (BIP39 seeds, Shamir, XOR, BIP85, BIP84) that is being extended to sign Bitcoin transactions (PSBT).
Hardware: PIC32MM0256GPM036 (256 KB flash, 32 KB RAM), XC32, MPLAB X project in `BIP39_MCC.X`, single configuration `v2`.
The old v1 hardware (PIC32MM0064GPL028) was removed from this branch; do not reintroduce `v1`/`v2` conditional compilation.

## Rule 1 - English only

All code written or modified for this project must be in English:
- identifiers (functions, variables, types, macros, files)
- comments (inline, block, Doxygen)
- log/debug strings, commit messages and documentation

Do not translate existing non-English code unless asked, but anything new must be English.

## Rule 2 - No git commits

Never run `git commit`, `git push`, or any other command that records or publishes changes. The user reviews the diff and makes all commits personally. Leave changes in the working tree and just summarize what changed; do not offer or ask to commit.

When the user asks for commit text, first look at `git log` and the staged diff (`git diff --cached --stat`): the text covers only what is staged and not yet committed, never work the user already committed. Give it in this format, short:
- First line: a short summary, up to about 70 characters.
- A blank line.
- A body of a few lines, wrapped at about 72 characters (a sentence or two on what changes and why, and a short `-` list only if there are several separate changes). No file lists, no memory figures.
- No `Co-Authored-By` or other attribution lines.
- English, as everything else (rule 1). List the new files that need `git add` (and any `-f` for ignored ones) outside the commit text, in the reply.

The open work list is `docs/pending.md`: update it whenever a task is done, decided or added, so the user can read it without asking.

## Rule 3 - Memory is tight (RAM and flash)

Even on v2 the budget is limited. Every change must be justified against it.

v2 budget (last build of `Seedmate_v2`):
- Flash: 238 KB usable (0x9D004000, 0x3B800; the first 12 KB belong to the bootloader, the next 4 KB to the app vectors, 0x9D003000, and its reset block, 0x9D003800). Used about 223.8 KB (229,207 B, 94.0% of the 238 KB left after the settings page).
- RAM: 32 KB (0x80000000, 0x8000). Used about 23.4 KB (24,008 B, 73.3%); the stack is what is left, 8,208 B (`_splim` 0x80005FE0 to `_stack` 0x80007FF8, the bootloader flag below inside it). Stack measurement: `stack_paint()` fills the free stack with `STACK_FILL` at power-on and in every `stack_wipe()`, `stack_peak_bytes()` finds the deepest word that lost it (peak since power-on), shown as "STACK PEAK used/size B" on SETTINGS > MCU SERIAL NUMBER (yellow over 7/8), with the flash lock state under it. Stack guard (audit R2): `stack_check()`, called by `app_tasks()` (every wait for a key) and `led_busy()` (every progress step), stops the device with "STACK OVERFLOW" when the lowest stack word lost `STACK_FILL` (the unused 512 B heap lies below it, then `.bss`).
- RAM address `0x80007F00` is the bootloader shared flag (`UPDATE_FLAG_ADDR`); never place data there.
- Biggest RAM users today: UR fountain decoder buffers `pure_parts` (8.7 KB) and `mixed_frames` (3.2 KB), one block `fountain_ram` that a BBQr scan borrows whole, `next_beams`/`current_beams` (1.5 KB each), `fast_bw_lookup` (1.3 KB), the loaded multisig wallet `ms_wallet` (0.6 KB).
- Biggest flash users: `.text` (about 78 KB) and the BIP39 word list (about 5.7 KB, packed).

RAM guidelines:
- Avoid large local arrays and big static buffers; reuse existing buffers (for example share scratch space between screens that are never active together).
- No dynamic allocation (`malloc`/`free`); the heap is only 512 bytes.
- No recursion; keep stack depth shallow, especially inside crypto code (secp256k1, bignum).
- Prefer the smallest integer type that fits; pack structs.
- Wipe secrets (seeds, keys, mnemonics, nonces) with `memzero` as soon as they are no longer needed.

Flash guidelines:
- Keep constant tables `const` so they stay in flash.
- Text on black at size 1 goes through `text_at(x, y, text, color)` (`screens.c`, not inlined: two arguments fewer in each of 500 calls, 2.8 KB), never `drawtext(..., ST7735_BLACK, 1)`; a number appended to a line is `strcat_num(line, n)`, not `fast_itoa()` into a temporary and `strcat()`.
- Avoid `printf`-family and floating point; they pull in large library code.
- Do not add or enable crypto modules, curves, or wordlists that are not strictly needed.

After any change that adds code or data, rebuild `Seedmate_v2`, read the memory report (`dist/v2/production/*.map`, "Total ... used") and mention the flash and RAM delta in the summary.

## Rule 4 - Transparency and user control come first

The user must always see what the device is doing and stay in control. This is a priority in both the interface and the flow logic, on the same level as security:
- Never sign, write to the SD card, export or change anything without an explicit confirmation step that shows what will happen (amounts, destinations, which keys/inputs).
- Long operations (key derivation, checks, signing, file I/O) show a progress bar plus the step currently running (for example "INPUT 2 OF 3", the derivation path, "SIGNING", "VERIFYING SIGNATURE"), and blink the activity LED (`LED`, RA2) every 150 ms: `led_busy()` in the progress callbacks (`pbkdf2_progress_bar()`, `key_progress_step()`, `psbt_progress_step()`, `vault_progress()`), `led_done()` at the last step and when a screen waits for a key (`wait_any_key()`, `psbt_wait_key()`). This covers the PBKDF2, key and BIP85 derivations, PSBT checks and signing, saving to the SD card, the vault and INITIALIZE CARD; WIPE ALL CARD calls `led_busy()` per sector and can be stopped with STOP (BACK), saying where it stopped. A new long operation uses these callbacks, or calls `led_busy()` / `led_done()` itself.
- When something is refused or fails, say why on screen in plain words ("PREV TX MISMATCH", "SWITCH TO MULTI SIG", "TYPE NOT SUPPORTED"); never fail silently or fall back to a different action. Keep these texts short, a few words naming the cause (every string costs flash), and give the specific reason rather than a generic one ("NOTHING TO SIGN" only when no other reason applies).
- Show verified facts and unverified claims differently (colors, "VERIFIED" / "NOT VERIFIED" labels); do not present data from the PSBT as checked when it was not.
- Every flow can be cancelled with BACK before any irreversible step.

## Rule 5 - No real wallet data in the repo

Never put data from the user's real wallets (xpubs, descriptors, fingerprints, addresses, QR captures or exports) in source, test or documentation files, not even temporarily: it reveals the wallet's addresses and balances. Test data comes from generated test seeds ("abandon x11 about" and seeds derived in the Python generators). If the user shares a real export to show a format, use it only to learn the format and rebuild an equivalent from test keys.

## Rule 6 - Button grid on every screen that waits for a key

Whenever a screen waits for a key, show the button grid (bottom right, x 63-153 from `GRID_X` in `screens.h`, y 105-125: BACK, UP, OK on the top row, LEFT, DOWN, RIGHT on the bottom row) with what each button does on that screen, and only the buttons that do something. Do not describe keys in text footers ("OK=SIGN BACK=CANCEL", "PRESS ANY KEY"); the one exception is what a grid cell cannot say, a key that also acts when held, as a short note at the left of the grid (raw dice: "HOLD BACK / TO DELETE"). Use the helpers in `screens.c` (`grid_menu2()`, `grid_OK_back()`, `grid_confirm()`, `grid_labels()`...) and add a new `grid_*()` there when no existing one fits. Lay out the screen so nothing is drawn inside the grid area (progress bars go above it, at y 92-97); only full-screen QR codes may leave it out, and the start screen, which keeps "PRESS ANY BUTTON" under the logo on purpose. Label OK (and BACK) with the action when it is specific ("QR", "SAVE", "STOP", "UPDT"), not a generic "OK".

## Rule 7 - Consistent colors

Every color has one meaning on every screen; reuse it, never pick a color for looks:
- WHITE: normal text: menu options, values and data (words, addresses, xpubs, amounts), labels of keys and the explanations in the body of a screen. Light gray `ST7735_LIGHTGREY` (0xC618, `screens.h`): only the screen title, the top line, always drawn centered with `draw_title()` (`draw_title_pair()` when a second part shares the line, e.g. "INPUT 1/3" and the script type); error and success screens keep a red or green title, also centered. The main menu has the title "SEEDMATE". Dark gray `0x8410`: disabled items and decoration (key outlines); the darker `0x4208` only for the bands of the PSBT flow diagram.
- YELLOW: warnings and unverified data ("NOT VERIFIED", "AMOUNTS NOT VERIFIED", warnings that do not stop the flow), and the fee.
- ORANGE: only the selected item or cursor (menus, keys, editable fields). Not for titles, hints or amounts.
- GREEN: success and verified facts ("VERIFIED", "OK", "LOADED", our own key or fingerprint), also as the title of a success screen.
- RED: errors, refusals and dangerous actions ("PSBT PARSE ERROR", "KEY MISMATCH", wipe), also as the title of an error screen.
- CYAN: secondary information and progress (derivation paths, counters, active layer), and what the device is doing right now ("DERIVING THE KEYS", "READING SD CARD...", "SCANNING...", the running step above a progress bar).
- Progress bar: white outline, green fill.
Texts are upper case. Before adding a screen, look at a similar existing one and copy its colors.

## Rule 8 - Every change gets its device test

Every new function, improvement or fix that changes what the device does gets a test in `docs/validation/firmware_validation.html` in the same change, without being asked: a new test with a stable id in the right section (steps, and the expected result with the known values of the abandon seed and the files of `test/`), or the `rev` of an existing test raised when its steps or expected result change. Say in the summary which tests were added or changed.

## Rule 9 - Do not break what works

A change must leave the rest of the firmware working, not only do its new job:
- Before calling it done, find every user of each function, struct, constant or stored format it changes (grep) and check each one; a changed stored format still reads what older firmware wrote (vault entries, settings records, SD slots), or says why it cannot.
- Build `Seedmate_v2` and run every host bench that compiles a changed file or extracts code from it (`extract_*.py`: psbt, words, entropy), plus the benches of the area (sdfiles, vault, bbqr, ur_anim, derive, kef...), not only the new test; a bench that fails is fixed before the change is reported.
- Say in the summary which existing device tests go through the changed code, when it touches code that other functions share.

## Building and checking (no IDE needed)

The project builds from the command line with MPLAB X's `make` and XC32 v5.10 (`-O1 -ffunction-sections -fdata-sections -mmemcpy -G 1024`, the last two in the additional options of the project, see `docs/flash-savings.md`; the interface files, and only them, add `-fcrossjumping -foptimize-sibling-calls -fcode-hoisting -ftree-tail-merge -fno-tree-ch -fno-move-loop-invariants -fno-tree-loop-im` as per-file options (`<item ... overriding="true">` at the end of `configurations.xml`: main, screens, psbt, descriptor, ur_encode, settings, snake, EFF_short, nostr and the generated init / clock / interrupt controller / GPIO / stdio files); cryptography and long running code keep the project options, and a new file gets them too unless it is added there; linked with `--gc-sections -G 1024`, no LTO, and `-Werror -Wall`, so any new warning breaks the build). From `BIP39_MCC.X`:

```bash
export PATH="/c/Program Files/Microchip/MPLABX/v6.35/gnuBins/GnuWin32/bin:/c/Program Files/Microchip/xc32/v5.10/bin:$PATH"
make -f nbproject/Makefile-v2.mk SUBPROJECTS= .build-conf
```

Add `-B` to force a full rebuild (the build is reproducible: same `.hex` from any clone or folder, procedure and published hashes in `docs/reproducible-build.md`; a fresh clone first needs `prjMakefilesGenerator`, below, since the makefiles are not in git). The memory totals are in `dist/v2/production/BIP39_MCC.X.production.map` ("Total kseg0_program_mem used" and "Total Data Memory used"). `nbproject/Makefile-*.mk` are generated by MPLAB X from its in-memory project model. If the IDE has the project open, editing `configurations.xml` by hand is NOT picked up: MPLAB regenerates the makefile without the new file and may overwrite the XML on save. When a source file is added or removed, tell the user to add it in the IDE (Source Files > Add Existing Item) or to close and reopen the project before building.

With the project closed in the IDE, edit `configurations.xml` and regenerate the makefiles exactly as MPLAB would (no hand patching), from `SW`:

```bash
"/c/Program Files/Microchip/MPLABX/v6.35/mplab_platform/bin/prjMakefilesGenerator.bat" "BIP39_MCC.X@v2"
```

## Source layout (`src/`)

- `main.c` - application core: a `state_t` state machine in `main()`, entropy sources (coins, dice, words, cards, timer), SD card driver over SPI3, BIP39 helpers, BIP85, BIP84 (xpub/addresses), Shamir/XOR/obfuscation, text editor, and `scan_ur_message()` which rebuilds a UR message (`ur:crypto-psbt` for SIGN, `ur:crypto-output` for IMPORT DESCRIPTOR) from animated QR frames received on UART2 from a GM861 scanner, or a BBQr series (`bbqr.c`: type P for SIGN and REVIEW PSBT, type U, a text file, for IMPORT DESCRIPTOR; the first format read is the one of the scan, the other gives "MIXED UR AND BBQR"; the parts and the inflate use `fountain_large_buffer()`, the result is joined at its start within the 8,750 bytes a PSBT may take; a code longer than the 850 character scan buffer is read to its end and dropped whole with "LOWER THE QR DENSITY" (BBQr: Sparrow's low and medium density fit; UR: only low, a UR fragment over the 250 B of a fountain part says the same and over 35 parts "UR MESSAGE TOO BIG"); refusals name the cause: "BBQR IS NOT A PSBT", "BBQR PARTS DO NOT MATCH", "BBQR FILE TOO BIG", "BBQR DATA DAMAGED"...).
  Menus: the main menu has 8 entries (CREATE, LOAD, BIP85, OPSEC, TOOLS, SD CARD, RESOURCES, SETTINGS); OPSEC holds Shamir, XOR, obfuscation and cards, TOOLS the QR reader, QR from text, EFF password and REVIEW PSBT. `cMAIN_*` are function ids kept in `main_pointer` while a flow runs (the flows test it), the menus map their positions to them (`main_menu_ids[]`, `opsec_menu_ids[]`, selection in `main_sel`, `opsec_pointer`, `tools_pointer`); `MAIN_RUN` runs the chosen function and `transition_to_main()` returns to OPSEC after an OPSEC flow.
  MIX ENTROPY (last entry of CREATE, `cSEED_mix`) is the XOR flow with `xor_from_create` set: `main_pointer` is `cMAIN_XOR` as for SEED WORD XOR, `print_xor_menu()` shows "MIX ENTROPY - XOR" with 2, 3 and 4 INPUTS (`menu_mix[]`), BACK from that menu returns to CREATE, `transition_to_main()` goes to the main menu instead of OPSEC (and clears the flag, as `idle_recover()` does), and the result is a new seed, so its transcript is asked before it is loaded (`transcript_pending()`).
  STOPWATCH (`TMR_INPUT` from CREATE): every timer sample goes into `stopwatch_ctx` (SHA-256, prefix "SEEDMATE STOPWATCH") and counts as 8 bits, so twice the presses of the raw 16 bits; the seed is the hash, written to `data_array_256b` when the count is reached (audit L4). The Shamir split uses the same screen for its own entropy and keeps the raw samples. POKER CARDS starts with `card_intro()`: put each card back and shuffle, "tc = TEN OF CLUBS", the ranks and suits; BACK returns to the size menu.
  ENCRYPTED (KEF) (`kef_export_run()`, design in `docs/kef.md`, title `KEF_TITLE`): yellow notice, the key in the editor (`editor_review_title` names its check screen), confirmation with the seed size, the ID and the real count (the KEF ITERATIONS setting plus Krux's random delta of up to 10%), always the fingerprint in lower case as Krux (derived with `derive_root_screen()`; no options, on purpose), progress, then the envelope is opened again and compared; the base43 text is then kept in `kef_text()` (start of the fountain buffer, since `buffer` does the SD I/O and the slot previews) and `KEF_OUTPUT` offers SHOW QR (the same viewer as QR FROM TEXT, `qr_from_kef`: BACK returns to this menu) and SAVE TO SD CARD (`kef_sd_mode`: the same slot list, marker check and overwrite question as the unencrypted backup, `sd_write_kef()` writes, reads back and compares); BACK wipes the text and returns to SEED BACKUP. Not blocked by the SEEDQR or UNENCRYPTED SD SAVE settings: it is encrypted. An encrypted slot is "SEEDMATE KEF", version 1, the text length (2 bytes, big endian) and the base43 text from byte 16 (`sd_sector_is_kef()`); `load_and_verify_sd_slot()` opens it through `kef_load_from_qr()` (ID, iterations, key, retry), so every load from SD (LOAD, triple, Shamir split and merge, XOR, BIP85, obfuscation, cards) takes encrypted slots, sets `size_pointer` itself, and returns 3 when the key was not given (the caller draws its list again); the slot previews say "KEF", the overwrite question and the INITIALIZE / WIPE count know it. Every seed read by QR passes first through `kef_load_from_qr()`, so it also works for XOR, Shamir, BIP85, cards and obfuscation: `kef_parse_text()` says whether the text is an envelope (base43, not all digits, 12 to 24 word sizes), the ID, the iterations and the estimated time are shown (`kef_time_text()`, 44 s per 100,000 measured), the key is asked, "NOT DECRYPTED / WRONG KEY OR DAMAGED QR" allows another try; the entropy is then in `data_array_256b` like a Compact SeedQR. QR READER only names it ("ENCRYPTED SEED (KEF)").
  SEED BACKUP: the LEFT arrow of the words screen (label "SEED BACKUP") opens `BACKUP_MENU` (UNENCRYPTED SD, SEEDQR, COMPACT SEEDQR, ENCRYPTED (KEF), VERIFY TRANSCRIPT; `menu_backup[]`, `draw_backup_menu()`: its BACK key is labelled LIST since it returns to the words). VERIFY TRANSCRIPT (`transcript_verify()`) checks the paper copy: every word in order, four choices each (the right one and three of the 12 words around it in the alphabetical list, so a word copied wrongly is the one picked; random order), the cursor in orange; BACK returns to the list, a wrong word says which one in red and returns to the whole list, all right gives "TRANSCRIPT VERIFIED" in green. WALLET (OK, or RIGHT labelled "WALLET") on the words of a seed just made with CREATE asks for it first (`show_seed_load()`, `transcript_pending()`), with a red "SKIP AND LOAD" row below the words, reached only going down; once verified or skipped the seed is remembered (`transcript_tag`, a short hash of the entropy, wiped in `transition_to_main()`) and LOAD does not ask again; loaded seeds are never asked. SEEDQR and COMPACT SEEDQR are blocked with the reason on screen (`print_blocked()`) when the SEEDQR setting is off, otherwise the red warning comes first, once per session (`warned_seedqr`, cleared in `transition_to_main()`); the viewer (`VIEW_QR`, `draw_seed_qr_view()`) shows the code full screen, OK zooms into one tile (`draw_qr_view()` in `screens.c`: at most 15 modules per tile side, neighbouring tiles share one module, grid lines, row/column numbers every 5 modules; 2x2 tiles for a seed QR) and the arrows move between tiles. UNENCRYPTED SD (the XOR slot) is blocked when UNENCRYPTED SD SAVE is off, otherwise a yellow warning (`print_sd_warning()`: not encrypted, erase after use or keep the card apart from this device) precedes the slot list, once per session (`warned_sd`, cleared in `transition_to_main()`). Seeds are written only to slots 2..200 (sectors 1..199, `cSD_WRITE_LAST_SLOT`): slot 1 (sector 0) belongs to older firmware and is read only, and nothing else on the card is touched. A slot that already holds a valid seed (checksum as `sd_write_seed()` writes it) asks for confirmation first ("SLOT n IS IN USE", BACK / OVER); `sd_write_seed()` wipes the sector buffer afterwards. The SD slot format is XOR with one byte plus a checksum: obfuscation, not encryption.
  SD card layout (`app_defs.h`): sector 0 is the legacy slot 1 (read only), sectors 1..199 are seed slots 2..200 (ERASE SECTOR only accepts these: "NOT A SEED"), the vault header is sector 501 and its records 502..2046 (`vault.h`, `docs/vault.md`), and sector 2047 (`cSD_MARKER_SECTOR`, last of the first 1 MB, never used by older firmware) holds the marker "SEEDMATE" + format version + complement of the sum of those 9 bytes (`sd_marker_build()`, `sd_marker_valid()`). The SD CARD menu (`menu_erase[]`) has ERASE SECTOR, INITIALIZE CARD and WIPE ALL CARD. INITIALIZE CARD (`sd_initialize_card()`; first the seeds it would erase are counted over sectors 0..2046 with a progress bar, `sd_count_seeds()` with the strict `sd_sector_is_seed()`: checksum, size and every other byte zero, as this firmware and the first Seedmate write them; then the red warning, which says "n SEEDS WILL BE ERASED" in red or "NO SEEDS FOUND ON IT"; progress bar with the step: erasing the first 1 MB, writing the vault header, writing and verifying the marker) zeroes sectors 0..2046, so it destroys the seeds, the vault and any file system, writes an empty vault header with a new `vault_id` and a random first counter (`vault_new_id()`: SHA256 of the Shamir key press pool `sss_entropy_pool`, TMR1, the core timer and "VAULT"; the pool is cleared afterwards since both are public) and reads it back, and writes the marker last; WIPE ALL CARD (the seeds of the first 1 MB counted first, as for INITIALIZE CARD, then the red warning with the card size and "n SEEDS WILL BE ERASED") overwrites every sector with 0xAA from sector 0, marker included, so the card becomes uninitialized; it shows a progress bar and STOP (BACK: "WIPE STOPPED AT n MB", and "SEEDS MAY REMAIN" when stopped in the first 1 MB). Seed writes require a valid marker (`sd_marker_state()`, checked when SD is chosen in SEED BACKUP and again before each write, "CARD NOT INITIALIZED" / "USE SD CARD > INITIALIZE CARD"); reads of slots never depend on the marker, so cards from older hardware still load. Keep one card only for seeds and never put it in a PC (a PC would offer to format it); use another card to move PSBTs, descriptors and firmware: FAT16 (the bootloader reads only FAT16; the app reads and writes FAT16 and FAT32).
  TOOLS: QR READER (`reader_open()`, `QR_READER`) reads one code with `qr_read_raw()` (stored scanner setup, UART2 interrupt ring, spaces and binary kept, into the fountain buffer, wiped on exit; the only scanner read besides the animated UR scan: the seed QR (`QR_SCANNING`, `keep_tail` so a Compact SeedQR ending in 0x0A or 0x0D keeps every byte, BACK cancels while waiting) and SCAN ADDRESS use it too) and only shows it: a type label for information (text or binary size, bitcoin address, payment URI, one UR part, one BBQr part, yellow "LOOKS LIKE A SEED" / "COMPACT SEEDQR"), the content wrapped in pages (UP/DOWN), binary in hexadecimal; nothing is loaded or saved. QR FROM TEXT (`text_qr_edit()`) edits up to `cTEXTQR_MAX` (320) characters in the note editor, with a fixed gray title and its save key labelled GEN QR (`editor_title_fixed`: no title editing, no UP hint), kept in `buffer` while shown, then shows the QR in the same viewer as the SeedQR (zoom by tiles, so a passphrase QR can be copied by hand), the smallest version up to 11 with error correction M, or L if M does not fit (`draw_text_qr_view()`; the QR library does not check capacity, `text_qr_bits()` does); a text that is a seed (`text_looks_like_seed()`: 12-24 BIP39 words or 48/96 SeedQR digits) gets a red warning first, whatever the SEEDQR setting; BACK from the QR returns to the text, CANCEL in the editor wipes it.
  REVIEW PSBT (TOOLS, `psbt_inspect_only`): the same FROM QR / FROM SD menu and PSBT viewer as SIGN, without a seed and without signing: no SIGN in the grid (OK is NEXT page), the flow says "NO SEED / UNCHECKED" with yellow inputs and outputs named OUT n, the details "NO SEED: KEYS NOT CHECKED", and key lines show "FP xxxxxxxx NOT CHECKED" in yellow; BACK from the menu returns to TOOLS. SIGN and IMPORT DESCRIPTOR in the wallet menu clear the flag.
  EFF PASSWORD (TOOLS, `eff_open()`, `EFF_CONFIG` / `EFF_ROLL` / `EFF_RESULT`): 1..12 words (`cEFF_MAX_WORDS`) of the EFF Short Wordlist 1, each from 4 dice entered on the 1-6 keys (LEFT/RIGHT, OK, DEL removes the last die or the last word); the index is the dice number, as in the printed list, so it can be checked by hand; the dice are the only source of the words. Optional NUMBERS: one digit after each word from the timer when the word is completed (`timer_digit()`). Optional 1ST LETTER CAPITAL (`eff_capital`): the first letter of each word in capital, for sites that ask for one (no entropy added). SEPARATOR (`eff_sep`): space, "-" or "_" between words. The configuration screen has one row per option (WORDS, NUMBERS, 1ST LETTER CAPITAL, SEPARATOR): UP / DOWN move between rows (circular), LEFT / RIGHT change the value of the row and the grid names them (`grid_rows_keys()`): "-" / "+" on the words (1..12 circular), NO / YES on the two options, and on the separator the one each key would load (rotating). The words are shown in lower case on the dice screen and in the result (exactly as typed, unlike the other upper case texts), with the separator chosen (named at the top of the result); the configuration screen shows the entropy of the result as one total ("ENTROPY: n BITS", rounded down: 10.34 bits per word, 13.66 with the digit), updated with each change; OK shows its QR in the zoomable viewer (`qr_from_eff`: BACK returns to the result). The EFF code no longer uses `buffer` for itself (TOOLS keeps the result text there while it is shown). Everything is wiped on exit. The list (`EFF_short.c`, packed as `wordpack.h`) is generated by `../test/eff/gen_eff_short.py` from the official file (SHA-256 8f5ca830...ae69) and `../test/eff/test_eff.c` rebuilds that file from the firmware list and checks the hash; do not edit the list by hand.
  Text editor (`full_text_editor()`, BIP39 passphrase and notes): 3 alphabetical rows of 9 outlined keys plus CANCEL/SAVE and a last row split in RETURN / QR / die (`KBD_QR`, `KBD_DIE`), the 2x3 control keys (aA, 0# for the NUM and SYM layers, cursor arrows) next to the untouched `grid_keyboard()`; NUM and SYM layers hold each printable ASCII symbol once. QR (`editor_qr_read()`) opens the QR READER screens in insert mode ("INSERT FROM QR", `reader_insert`): the text is shown in full with its length and ADD inserts it at the cursor (title or text) only if it is printable ASCII (line breaks only in the note text, CR dropped) and fits what is left, otherwise the reason in red; it reads into the last 512 B of the fountain buffer (the editor text is in `buffer`, a vault list at the start of the fountain buffer). The die runs the EFF PASSWORD screens as a blocking call (`eff_generate()`, same `eff_key_press()` handler as TOOLS, `wait_any_key()`) and inserts the password at the cursor, or says it does not fit ("NOT INSERTED"). Passphrase mode adds a character counter and a review screen after SAVE (BACK edits again); `edit_bip39_passphrase()` edits a copy, so CANCEL keeps the old one, and `transition_to_main()` wipes it.
  XOR and Shamir merge ask the source (keyboard, SD, QR) before each input: `print_input_menu()` shows "SEED n OF m FROM" / "SHARE n OF k FROM" and the inputs already loaded, and every source ends in `multi_input_store()` (size check against the first input, XOR or interpolation after the last one); `multi_input_wipe()` clears the inputs at the start, on cancel and after the result.

  AUTO UNLOAD (SETTINGS, `idle_option`, `menu_idle[]`): no key for the chosen time wipes everything and returns to the main menu. The time runs in `app_tasks()`, which every wait for a key calls (a new wait loop must call it, not `SYS_Tasks()`, which is empty); a key, `led_busy()` (so any long operation with a progress callback) and a QR being read restart it, and it does not run on the start and main screens. It leaves the flow with `longjmp()` to the loop of `main()`, so `idle_recover()` wipes what the flow would have (`session_wipe()`, the same as UNLOAD SEED, plus the stack below `main()`, `stack_wipe()`, from `_splim`), clears the mode flags the flows leave set (a new flag of that kind goes there), and says why on screen. While the scanner interrupt is on (`scan_rx_start()` / `scan_rx_stop()`, `idle_hold`) the jump waits: the UR scan leaves as with BACK (`idle_expired()` in its loops), restores the scanner, and the next wait fires it.
